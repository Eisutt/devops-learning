# 01. Подготовка: репозиторий и сервер

## Цель

- Создать репозиторий для документирования обучения.
- Поднять учебную ВМ в Yandex Cloud и подключиться к ней по SSH-ключу.
- Снять базовую информацию о сервере.

## Что сделал

### 1. Репозиторий на GitHub

Создал публичный репозиторий на GitHub и связал его с локальным каталогом на Mac:

```bash
echo "# devops-learning" >> README.md     # создать README
git init                                   # инициализировать git-репозиторий в текущем каталоге
git add README.md                          # добавить файл в индекс (staging area)
git commit -m "first commit"               # зафиксировать изменения
git branch -M main                         # переименовать текущую ветку в main (-M: принудительно, даже если main уже есть)
git remote add origin https://github.com/Eisutt/devops-learning.git   # добавить удалённый репозиторий под именем origin
git push -u origin main                    # отправить ветку main на GitHub; -u связывает её с origin/main (upstream)
```

После `-u` дальше достаточно писать просто `git push` и `git pull`.
Следующие коммиты и пуши делаю через VS Code (вкладка Source Control).

### 2. Виртуальная машина в Yandex Cloud

| Параметр | Значение |
|----------|----------|
| ОС | Ubuntu 24.04 LTS |
| Платформа | Intel Ice Lake |
| vCPU | 2 |
| Гарантированная доля vCPU | 50% |
| Прерываемая | нет |
| RAM | 2 ГБ |
| Диск | 20 ГБ |

Сначала создал ВМ с долей vCPU 100%, потом снизил до 50% для экономии гранта.
Для этого ВМ нужно остановить, затем в **Редактировать → Вычислительные ресурсы** поменять долю.

Почему не прерываемая: такая ВМ дешевле, но её останавливают в любой момент и обязательно через 24 часа работы,
а запускать её обратно приходится вручную. Для постоянно работающих сервисов и мониторинга это неудобно.

**Гарантированная доля vCPU** — это процент времени физического ядра, который гарантирован ВМ.
При 50% ВМ может кратковременно использовать ядро полностью, но гарантированы ей только 50%.
Для учебного сервера без постоянной нагрузки этого достаточно.

Бюджет с ограничением не настраивал: расходы идут из гранта на 10 000 ₽.

Для доступа использовал уже существующий SSH-ключ: при создании ВМ вставил его публичную часть (`.pub`).

## Вопросы

**1. Чем отличаются приватный и публичный ключ, и где каждый из них должен лежать?**

- **Приватный ключ** хранится только у владельца, на клиенте в `~/.ssh/`, с правами `600`.
  При более открытых правах SSH откажется его использовать. Никому не передаётся.
- **Публичный ключ** кладётся на сервер в `~/.ssh/authorized_keys` того пользователя, под которым входишь.
- Как проходит аутентификация: сервер отправляет клиенту задачу, клиент подписывает её приватным ключом,
  сервер проверяет подпись публичным. **Приватный ключ никогда не передаётся по сети.**

**2. Что значит «прерываемая ВМ», и чем это может навредить в продакшене?**

Прерываемая ВМ в Yandex Cloud:
- может быть **принудительно остановлена в любой момент**, если ресурсы понадобились в зоне;
- **гарантированно** останавливается через 24 часа работы, даже под нагрузкой;
- сама обратно не запускается: нужно стартовать вручную или через instance group;
- стоит в несколько раз дешевле обычной.

Чем вредит в продакшене: внезапный простой сервиса и потеря всего, что было в памяти и не успело записаться на диск.
Подходит для задач, которые можно прервать без последствий: тестовые стенды, CI-раннеры, пакетные вычисления.

**3. Зачем нужна passphrase на SSH-ключе?**

Passphrase **шифрует файл приватного ключа на диске**. Это локальная защита:
она не передаётся на сервер, и сервер о ней ничего не знает.

- **Ключ без passphrase** лежит на диске в открытом виде. Если украдут ноутбук или скопируют файл
  (вирус, бэкап, забытая флешка), злоумышленник сразу заходит на все серверы, где лежит публичная часть.
- **Ключ с passphrase** без фразы бесполезен. Злоумышленнику придётся её подбирать,
  а за это время можно успеть удалить скомпрометированный ключ из `authorized_keys` на серверах.

Чтобы не вводить passphrase при каждом подключении, используется **ssh-agent**:
он хранит расшифрованный ключ в памяти на время сессии. На macOS он умеет сохранять passphrase
в связке ключей (Keychain), опции `UseKeychain` и `AddKeysToAgent` в `~/.ssh/config`.
